# 004. Graphical user interface

- Status: Accepted
- Date: 2026-11-27

## Context

Tests take seconds to hours, must be stoppable at once, and the person running them needs to see what is happening. Lecture 19 sets out the principles for a machine-control GUI: design the window first, keep the model separate from the view, never block the event loop, make STOP large, red and on a key, validate input, and convert units at the boundary.

This project needs more than the lecture's jog panel:

- live data from the real rig later (the hub samples at 1 kHz);
- about fifteen different tests (see the characterization test list), with more to come;
- a software STOP that disables the drives within milliseconds, as one of several layers of safety.

What the window must do (designed first, as in Lecture 19, slide 15):

| | |
| --- | --- |
| Inputs | Rig (simulated now, hardware later); test; that test's parameters, with units and limits |
| Outputs | Live plot; progress (trial, time left); result (for example Kt ± 95% interval, R²); always-visible readings of current, speed, bus voltage and temperatures; status message |
| Actions | Start, STOP, open the results folder |
| Safety | Limits on every parameter; bad input refused with a plain message; large red STOP on Esc; closing the window stops the test and disables the drives first |

## Options

### Toolkit

| Option | For | Against |
| --- | --- | --- |
| Tkinter (Lecture 19) | Ships with Python; simple; exactly the lecture's examples | matplotlib is slow for real-time plots; fewer widgets for a larger app |
| PySide6 (Qt) | Professional toolkit, named in Lecture 19 for "professional desktop GUI"; pyqtgraph for fast real-time plots; number boxes with built-in units and limits; tabs and panels for a growing app; LGPL licence | Larger install (PySide6-Essentials is about 82 MB); about a day to learn; CI needs extra setup on Ubuntu |
| PyQt6 (Qt) | Same toolkit as PySide6 | GPL, or a paid commercial licence |
| NiceGUI (web) | Modern look in a browser | Browser plus server for a local rig app; not covered in the course |
| Streamlit (web) | Quick dashboards | Re-runs the whole script on each interaction; custom threads can't update the page without an unofficial workaround |

### How a long test runs without freezing the window

| Option | For | Against |
| --- | --- | --- |
| A. Worker thread | Procedures stay straight-line code that reads like the papers' methods; they run unchanged in tests; the window never blocks, so STOP is always instant | The worker must never touch widgets; threads take care to test |
| B. Procedures split into steps, run by a timer | Single-threaded, like the lecture's arm animation | Every procedure rewritten as steps; a single slow call (such as reading 7 s of torque) still freezes the window |
| C. asyncio | Explicit waiting points | Qt and asyncio need glue code; most complexity for least gain |
| D. Separate process | Strongest isolation between the window and the test | Passing data between processes adds complexity; overkill for now |

In both A and B, a procedure's `wait(1.0)` is part of the test method (for example, Lee et al. 2019 hold each current for 1 s before recording), so on hardware the test runs in real time either way. The choice only decides which part of the program keeps the timeline.

### Command line

Options: GUI only, or GUI plus a command line for scripted runs.

## Decision

- **PySide6** (the `PySide6-Essentials` package) with **pyqtgraph** for live plots. Lecture 19's ideas carry over directly: `QApplication.exec()` is the event loop, signals and slots are events and callbacks, `QGridLayout` is `grid()`, `QTimer` is `after()`, and `QDoubleSpinBox` shows units and limits next to every number.
- **Worker thread (option A).** The test runs in a standard Python thread. It puts its progress, data and results in a thread-safe queue, and the window reads that queue every 50 ms with a `QTimer`. I chose this over Qt's own threads and signals because the code that runs tests then never imports Qt, so it can be tested without a display, and because 1 kHz data is naturally batched into about 20 redraws per second.
- **STOP acts at once.** It sends disable commands to every drive directly from the window, with a lock so it can't interleave with a test command, then tells the worker to finish. The clock's `wait()` returns early when stopped, and the procedure's cleanup calls `disable()` again, which is safe to repeat (decision 001).
- **Model, controller, view** (Lecture 19, slide 16):
  - Model: the `motorbench` package (procedures, rig, simulator, analysis). No Qt.
  - Controller: `RunController` owns the worker thread, queue and stop signal, validates parameters and converts units. No Qt.
  - View: the PySide6 window. It builds widgets, reads the queue and draws.
- **The window builds itself from the tests.** Each procedure declares its parameters (name, unit, limits, default) and the live views it wants (for example "torque vs current" or "temperature vs time"), so adding a test needs no GUI code. The test list comes from the `TestProcedure` subclasses (polymorphism, as in Lecture 18).
- **Units at the boundary.** The model stays in SI units; the window shows rpm, °C and similar.
- **Simulation speed.** The simulated clock can run at 1×, 10× or as fast as possible, so a demo looks like the real rig and tests stay fast.
- **No command line for now.** `uv run motorbench` opens the window. Unattended hardware runs can use `pytest -m hil`, and a command line can be added later without changing the model.
- **Testing.** The controller gets ordinary unit tests. The window gets a smoke test with pytest-qt that opens it and runs a short simulated test.

## Consequences

- New dependencies, added with `uv add` when the GUI code is written: `PySide6-Essentials` and `pyqtgraph` (runtime), `pytest-qt` (development).
- On Ubuntu, CI needs Qt's system libraries and a virtual display for the GUI test (the `setup-qt-libs` action recommended by pytest-qt, plus Xvfb). Windows CI opens windows normally.
- The model and controller never import Qt. The worker never touches widgets; it only writes to the queue.
- The clock gains a stop signal: `wait()` returns early and raises `TestStopped`.
- The software STOP is one of four safety layers, from most to least independent: the physical E-stop; the ODrive's own limits and watchdog (the axis goes idle if the PC doesn't feed it within `watchdog_timeout`); the hub's watchdog (firmware, later); and the software SafetyMonitor and STOP.
- Python paces commands at about 10 Hz or slower and only triggers faster events. Since Python 3.11, `time.sleep` on Windows has 100 ns resolution, but the operating system can still delay a thread by milliseconds. Fast waveforms and control loops (random excitation for cradle resonance, sine sweeps for current-loop bandwidth, cart emulation) must run on a device. That is a hardware-phase decision.
- PySide6's LGPL licence allows continued development, including closed-source use, as long as Qt stays a separate, replaceable library and its licence notices are included.
- Schedule: the GUI replaces the command line in week 2, and the back-EMF test moves to week 3.
- Learning Qt costs about a day at the start of week 2.
